**2026-10-15** · Christof Buchbender · buchbend/lore#522

**Why:** The `build` skill gave two answers for the epic PR. `SKILL.md` let it merge only after the user's yes. `epic-tail.md` merged it on green checks. The reviewer of [#514](https://github.com/buchbend/lore/pull/514) (teach the workflow skills to keep the roadmap) found the conflict. [#518](https://github.com/buchbend/lore/issues/518) (one merge rule for the epic PR) recorded it.

**What we did:** The owner chose the stricter rule. The epic PR into `develop` or `main` waits for the merge approval, and an unreachable user leaves the PR open. Feature PRs into the epic branch still merge without the user, so an epic run stays AFK until its tail. We changed `epic-tail.md`, not `SKILL.md`, because the rule in `SKILL.md` already named the epic PR. A deploy gate now rides in the same approval message, so the user answers once. `CONTEXT.md` defines merge approval.

**Consequences:**
- A person who runs an epic gets one question at the end: merge the epic PR or not.
- Nobody outside this repo notices otherwise.
