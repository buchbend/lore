**2026-11-18** · Christof Buchbender · buchbend/lore#644

**Why:** Planning an epic cost more than building a well-cut slice. `to-epic` split work into a new epic at each change of topic. The orient homework also filled the context with 5 to 8 raw tool results.

**What we did:** One epic can now hold several topics, with one PRD section per topic. `to-epic` splits only on release order, not on topic ([ADR 0023](https://github.com/buchbend/lore/blob/main/docs/adr/0023-epics-split-on-release-order-not-topic.md), epics split on release order). A slice can hold substeps, and each epic carries a review plan. Each lens runs once at the epic end over its rows, not on every row, because one pass sees the rows side by side. The context pack takes an `intent`. `lore brief` returns the filtered result in one call, and `lore.api` lets a script chain the lore tools. `lore workflow after-merge` does the routine steps after each feature merge.

**Consequences:**
- Users: orient calls `lore brief` first. A planned epic holds more rows.
- The epic lead runs one command after each merge.
- Nobody outside this repo notices.
