# ADR 0003: The session-note body is a deterministic render of the ledger

- Status: Accepted
- Date: 2026-07-12
- Context: epic [#282](https://github.com/buchbend/lore/issues/282),
  PRD [0008](../prd/0008-typed-fact-session-notes.md), sub-issue
  [#285](https://github.com/buchbend/lore/issues/285)

## Context

A session note was composed *forward*: each flush turned its transcript slice
into a chapter of prose, appended, and immutable thereafter (ADR 0001 relaxes
that only for a session reopening its own note). The file was therefore a
concatenation of what the model believed at each point in the session.

That structure guarantees three defects, independent of prompt quality:

- **Interim states persist as facts.** "Features #514–#516 remain in progress"
  is false by the end of the note that contains it. Append-only-until-close
  makes this the steady state of any long session.
- **Process narration crowds out substance.** Which facts matter is only
  knowable *backward*, at the ending. At flush time "PR #524 opened" genuinely
  is the substance of its slice; only the ending reveals that twenty such
  blocks collapse into "all five features merged".
- **Model prose becomes the record.** The composed body was the only copy of
  what the session established, so a later reader — human or LLM — had nothing
  else to check it against.

Typed-fact extraction (PRD 0008) replaces the composed chapter with a ledger of
typed facts, each carrying a kind, a thread key, checkable refs, an anchor, and
a code-attached verbatim quote. That makes a second question unavoidable: is the
note the ledger, or something computed from it?

## Decision

The note file is **disclaimer + rendered note + ledger**, and the two lower
layers hold different contracts:

- The **ledger is append-only** — the existing contract, unchanged. Facts,
  prose chapters, and failure markers accumulate; a fact is never edited or
  deleted once written, and every fact keeps its quote and `@N` anchor.
- The **rendered body above it is derived state**: a pure function of the
  ledger, thrown away and recomputed in full whenever the ledger grows
  (`render_note`). Re-rendering the same ledger yields byte-identical output.

Rendering is deterministic code, with no LLM call anywhere in its path: fixed
section order (Done, Decisions recorded, Findings, Open), items sorted by
anchor, empty sections dropped, failed chapters read back as one-line coverage
gaps. One suppression rule de-noises the reading — a `progress` fact is omitted
when its thread later reaches a terminal fact — and suppression is a decision of
the *render*, never a deletion: the suppressed fact stays whole in the ledger.

This extends ADR 0001's carve-out. That ADR relaxed close-immutability so a
resumed session could *append* to its own note. This one states that the body is
not append-only at all: on the second close, the reading is rewritten over the
whole ledger rather than a second reading being stacked beneath the first.

## Consequences / Trade-offs

- **Positive — the note stops lying about its own ending.** Superseded interim
  states leave the reading automatically, because the render sees the whole
  session at once. Layout, ordering, and suppression are tuned with tests
  instead of prompt archaeology.
- **Positive — the grounding tier survives every rewrite.** The render is
  disposable, so getting it wrong costs nothing permanent: the facts, quotes,
  and anchors remain, and a better renderer can be run over the same ledger.
- **Positive — the reader can always check.** Every rendered line is traceable
  to its fact, its verbatim quote, and the transcript turn it came from.
- **Negative — the body is no longer a stable artifact.** A reader who cited a
  line of a note may find it re-rendered (though its fact is still in the
  ledger). This is acceptable under the note's own disclaimer: a lab-notebook
  record, never a source of truth.
- **Negative — the ledger boundary is a text boundary.** The render is
  regenerated by splitting the body at the first chapter delimiter, so no string
  entering the rendered part may contain a comment opener. This is enforced, not
  hoped for: every model- or transcript-derived string is neutralized before it
  is written (a marker opener inside a fact's own text would otherwise parse
  back out as a forged fact).
- **Ordering constraint.** The render must happen before the close, and the
  close is what freezes the file. A reopen re-renders; a closed note refuses to
  render.

## Alternatives considered

- **Keep the body append-only; render only the newest chunk's facts.** Rejected:
  it reintroduces the defect the epic exists to remove — a note whose ending
  cannot retire what its middle claimed.
- **Store the rendered note only, and drop the ledger.** Rejected: the ledger is
  the grounding tier. Without the quote beside the claim, a rendered line is
  exactly the unfalsifiable model prose this epic set out to eliminate.
- **Render on read (never persist the body).** Rejected: the note is a markdown
  file that other tools, editors, and humans read directly; a file whose body
  materialises only inside Lore is not a note anyone else can use.
