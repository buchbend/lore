# Lore UX Review — Extension to 2026-04-25 three-lens

This review extends the 2026-04-25 three-lens report rather than repeating it. Several issues called out then have already shipped fixes (`/lore:on` and `/lore:loud` skills now exist; help-grouping is restructured into Getting Started / Knowledge / Advanced; `lore status` exists and is well-shaped; SessionStart directive moved to the bottom). Findings below are what remains, plus issues a fresh read surfaces.

## 30-second pitch test

The pitch lands roughly half. The H1 sub-tag — "LLM-optimized knowledge graph for AI-coding teams" — is precise but abstract. By the time a smart new reader hits "The pitch", they already had to absorb a 6-line warning banner. Then the pitch itself opens with a metaphor ("decisions live in a chat window that disappears") which is good, but immediately drops into an ASCII pipeline diagram that reads as architecture, not value. **What's missing on screen one: a one-sentence example of what the user *sees*** ("Open Claude in any repo; Lore tells you what last week's session decided, then writes today's decisions back to git for you"). Verdict: technically correct, emotionally cold. NN/g: users decide "is this for me?" in 10 seconds (Nielsen, *How Users Read on the Web*, 1997, restated 2024).

## Top 7 UX issues (frustration severity × frequency)

### 1. The README has no diagram and no terminal screenshot — for a system whose entire pitch is "you'll see what happened"

**Where it bites:** First-time visitor on GitHub.
**What breaks:** Lore is an invisible-by-default conversational system. Every screenshot-equivalent in the README is ASCII-art *of the architecture*, never of the user-facing artifact (the SessionStart banner, `lore status`, `/lore:context` timeline). The actual format `lore 0.9.0: active · [[private]] · last note: … · 2 issues · 1 PR` — described internally as "the best surface in the product" — never appears in the README.
**What good looks like:** A single screenshot or fenced code block under "The pitch" showing a 3-line SessionStart banner from a real repo, plus one-liner: "This is what Lore puts at the top of every Claude session." A second showing `/lore:context` drill-down.
**Research:** NN/g — *Image-Focused Design* (Pernice 2017): users fixate first on imagery, descriptive text gets a fraction of the dwell. For tools where the *output* is the value prop, hide the architecture and show the output.

### 2. The "drill-down promise" works mechanically but is invisible to users who haven't read the SKILL.md

**Where it bites:** Mid-session. User sees `· consulted [[some-decision]]`. They want to dig in.
**What breaks:** There is no surfaced affordance. They'd have to know `/lore:context` exists, that it shows a *PID-keyed log*, that the log is the way to reach the raw transcript, and that `dangerouslyDisableSandbox: true` is needed (per `skills/context/SKILL.md:18`) just for the cache read. The status banner does not mention `/lore:context` exists. The wikilink itself is plain text: clicking it in a terminal does nothing.
**What good looks like:** Banner footer reads `· /lore:context to see what loaded · /lore:resume to load more`. Wikilinks in banner emit OSC-8 hyperlinks (terminal-clickable to a `file://` of the note) — almost no terminals fail gracefully, and the ones that don't just show the text.
**Research:** Nielsen heuristic 6, Recognition over recall — discoverability of next steps must be on the surface, not in docs. The current model requires recall.

### 3. Three install instructions disagree about what works

**Where it bites:** First five minutes.
**What breaks:** README §Install lists `pipx install git+https://...` then `lore install` then `lore init`. README §Bootstrap > "Fresh install" lists the same three commands but with `[capture]` extras and a different order (`lore init` before `lore install`). README §Marketplace says `/plugin install lore@lore` "alone gives you the plugin... it does not install the lore CLI itself." **A new user reads three orderings and three flags and cannot tell which is canonical.**
**What good looks like:** Single canonical block at the top of "Install" with a sentence saying "this is the only path you need; everything below is for special cases." Move "passive capture extras" into a one-line note: "Add `[capture]` to enable LLM-driven capture; defaults work without it."
**Research:** Hick's Law — when the same decision is presented N times with N different framings, decision time grows logarithmically with N. Users freeze.

### 4. Slash command toggles are now consistent but mean four commands for two states

**Where it bites:** Memory + tab-completion. Users stare at the autocomplete list.
**What breaks:** `/lore:on`, `/lore:off`, `/lore:quiet`, `/lore:loud` — four commands. `/lore:off` mutes everything. `/lore:quiet` mutes only inline citations. The cognitive overhead of remembering which is the broader hammer is real. Worse: the *names* don't telegraph the relationship. "Off" and "Quiet" are near-synonyms in English; nothing in the verb tells you "off is the bigger gun."
**What good looks like:** Collapse to two commands with arguments: `/lore:mute [citations|all]` and `/lore:unmute [citations|all]`. Default is `all`. Or, better, one toggle: `/lore:hush` cycles through `loud → quiet → silent → loud`. With a status line in `lore status` that says current mode.
**Research:** Jakob's Law — users expect commands to mirror real-world toggle vocabularies. Volume controls have one knob, not four buttons.

### 5. SessionStart directive is one terse line and reads like a scolding

**Where it bites:** Every single Claude session.
**What breaks:** `templates/host-rules/default.md` ends with "Asking about a wikilinked term without searching first is a bug." That's a contract violation framing aimed at *the agent* — but the user reads the same banner. Tone is corrective. There is no countervailing affordance pointing at what the agent will do that's helpful (e.g. "If you mention `[[term]]`, lore will pull context.").
**What good looks like:** `_Lore is loaded — wikilinks pull context automatically. Use /lore:context to see what was injected._` — same contract, framed as a capability.
**Research:** Banner blindness (Benway & Lane 1998; NN/g ongoing) — users skip text styled like instructions. A capability-framed line earns the slot; a directive-framed one is skipped.

### 6. `lore status` is well-designed; nothing tells the user it exists

**Where it bites:** The 2nd+ session. User is wondering "is anything happening?"
**What breaks:** The README mentions `lore runs show latest` and `lore doctor` in the Observability section but **does not mention `lore status`**. Yet `status_cmd.py` is exemplary: 7-line layout, decay-first ordering, loud-on-earning alerts. This is the answer to "what's Lore doing?" and it's hidden.
**What good looks like:** First line under Observability becomes: `lore status — am I doing anything for you right now? (run this first when in doubt)`. Sample output in fenced block. Then doctor / runs as deeper diagnostics.
**Research:** Visibility of system status (Nielsen heuristic 1). The whole product depends on the user trusting the background work; the command that *delivers* that trust is undocumented.

### 7. CLI / slash / MCP surfaces use three different vocabularies for the same operation

**Where it bites:** Every advanced user.
**What breaks:** Spot-check:
- "show me what was loaded" → `/lore:context` skill, `lore hook context-log` CLI verb, no MCP tool.
- "load context fresh" → `/lore:resume` skill, `lore resume` CLI, `lore_resume` MCP tool. Names match here — good.
- "look up notes" → `/lore:search` skill, `lore search` CLI, `lore_search` MCP tool. Names match. Good.
- "write a session note" → auto-capture via curator A (no user-facing verb). The `/lore:session` skill, `lore session new` CLI, and `lore_session_scaffold` MCP tool were all retired in favour of the single auto path; `lore session commit` survives as the wiki-side commit verb used by inbox/briefing.
- "make a wiki" → `/lore:new-wiki` skill (slash names exist with hyphens), `lore wiki new` CLI (subcommand form), `lore new-wiki` CLI alias. Three names per the maintainer's own instructions in `__main__.py:84`.

**What good looks like:** Pick the canonical noun-verb. CLI shipped `lore wiki new` already; slash commands and any remaining aliases should follow within one minor. One row in CONTRIBUTING.md saying *"every CLI verb has a slash mirror with the same word and an MCP tool with the same word; if it doesn't, it's a bug"* would make this self-policing.
**Research:** Consistency and standards (Nielsen heuristic 4). Users learn vocabulary once; cost compounds with every alias.

## Documentation gaps

- **No diagram of the data flow.** "What is Lore?" is a system question; the README answers it in prose. One block diagram (cwd → CLAUDE.md → wiki → SessionStart cache → Claude Code) would compress 800 words to a glance.
- **No "first 10 minutes" walkthrough.** README jumps from install to canonical shape to bootstrap to onboarding recipes. Missing: a literal transcript of what the user sees: the prompt from `lore install`, the banner from the first SessionStart, the format of `/lore:context` output. Show, don't describe.
- **`lore status` is undocumented in README.** See issue 6.
- **"What does Lore cost?" is not centralized.** Tokens spent at SessionStart, PreCompact, Curator A/B passes — these numbers exist (`hooks.py:8` cites 2.3s) but a token/$ table with sensible-default knobs would close the trust gap for skeptical first users.
- **CONTRIBUTING.md mentions a `~/.claude/plans/give-these-considerations-to-melodic-castle.md` link that 404s** (line 175). Internal artifact leaked.
- **No troubleshooting decision tree.** If SessionStart shows nothing, is it: no vault? no attach? hooks not wired? `lore install` not run? Currently the user's path is "read three sections of the README and run `lore doctor`." A flow diagram with three branches solves it in seconds.
- **Per-wiki `.lore-wiki.yml` is shown once with every knob set.** New users will copy it verbatim and get a confusing config to debug. Show the canonical empty file (zero lines), then show *only the override* for each common scenario.

## What's already great

- **`lore status`** as a piece of CLI design (`lib/lore_cli/status_cmd.py:1-20`) — activity-first, decay-ordered, loud-on-earning. The 7-line layout is exemplary; you should put a screenshot of it on screen one of the README.
- **The SessionStart status line shape** (`hooks.py:674`, `:790`) — `lore 0.9.0: active · [[private]] · last note: …` — is genuinely good information density. One token per concern, F-pattern friendly, reads left-to-right.
- **`attach_cmd.py:152-159` — the scope-conflict error message gives three explicit, ordered next steps** (`Decline`, `Rename`, `Ask the maintainer`). This is the gold standard for CLI error UX in this codebase; it should be the template for every other error path. Pair it with `hooks.py:684-688` ("set LORE_ROOT or run lore init") as the canonical examples in CONTRIBUTING.md.

## One big win

If you do one thing this week: **put a real terminal screenshot of `lore status` and the SessionStart banner under "The pitch" in the README**, with a one-line caption. The product's actual value is invisible until a user sees what's printed. Every other improvement on this list compounds on that base.
