# Roadmap

One paragraph: where the code is heading.

## Not placed yet

- **Next-run queue after a build.** A build run that files several follow-ups ends with a list of next runs: one command per issue, in an order. Today the list lives only in the final chat message. The handover section names the follow-up issues, not the order or the commands, and the archived ledger offers nothing after /clear. Lore should keep the queue in one home (the handover section or a seed issue) and name the next run at SessionStart, so a fresh session steps through the issues without the person remembering the list. Seen at the end of epic #555 (index-first context and the lab notebook) with follow-ups #564 to #567.
- **OpenCode toast through a TUI plugin entry point.** The @opencode/plugin 2.0.32 server Context has no toast; only the TUI plugin context (ui.toast.show) has one, and a TUI plugin needs its own tui entry point, not a single file in plugins/. Ship a small TUI entry so OpenCode shows a one-line 'Lore loaded' toast (PRD 0022, OpenCode as a host).
- **OpenCode token record: nested subagents.** The OpenCode token trace reads direct child sessions only. A subagent spawned by a subagent gets no row. Match grandchildren through their parentID chain.
- **Installer, first setup and onboarding.** A team that tries Lore needs value within 10 minutes. Today the first setup is hard to follow, even for the author on a fresh install. The hard part is the wiring: which wikis to attach, how scopes nest across repos, and which scope routes to which wiki. Lore should walk a person through that wiring in one guided `lore setup`. The setup shows the result as a map of repos, scopes and wikis. Then one short path follows. A person files one fact as an issue and finds it again from a second session. Every other feature stays optional and out of that path. The path is also the base of a public demo. PRD 0001 (trim Lore to the safe core) names the core.
- **Workflow that adapts to each team.** Lore leaves its context in places that humans already use: issues, PRs, ADRs and a git wiki. A team should keep that benefit without taking over the whole build workflow (orient, grilling, to-epic, build, review). A team chooses which skills and rules apply, and Lore keeps the filing rule and the context index. The per-wiki override of the writing rules shows the pattern. Lore should give the skills the same override, so a team can adopt one step at a time.
